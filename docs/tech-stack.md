## 2. 選定理由

### 2.1 前回との差異(課題の条件)

前回のタスク管理アプリで使用したReact・Java/Spring Boot・PostgreSQLとは異なる技術スタックを採用することが、今回の課題の条件である。フロントエンド・バックエンド言語・バックエンドフレームワーク・データベースの全てにおいて、前回とは異なる技術を採用した。

### 2.2 バックエンド言語・フレームワークの選定理由(Ruby / Ruby on Rails)

| 観点 | 内容 |
|---|---|
| 課題の条件との整合性 | Java/Spring Boot/Gradleを使用しないという条件を満たす |
| 講座内での言及 | 講座内でRubyが選択肢の例として挙げられていた |
| ジャンルとの適合性 | 問い合わせ・チケット管理という同ジャンルのサービス(Zendesk、Chatwoot、Intercom等)で、老舗・最新のプロダクトを問わず採用実績が豊富(2026年時点のWeb調査により確認) |
| 設計思想との対比 | Ruby on Railsは、前回使用したJavaの重厚なエンタープライズ的な書き方への反発として生まれた経緯があり、「異なる技術に挑戦する」という課題の趣旨に合致する |
| 今回の要件との関係 | Railsが強みを持つリアルタイム通信(ActionCable)は今回の要件(非同期のフォーム型問い合わせ管理)には含まれないため、この点で技術選定が左右されることはない。CRUD・認証・関連付けという今回の要件は、Ruby on RailsのActiveRecord・標準認証機能で十分に対応可能である |

### 2.3 フロントエンドの選定理由(Vue.js + TypeScript)

| 観点 | 内容 |
|---|---|
| 課題の条件との整合性 | Reactを使用しないという条件を満たす。TypeScriptは継続使用が公式に許可されている |
| アプリの特性との適合性 | フォーム入力・一覧の絞り込み・ステータス管理が中心の今回のアプリと、Vueのリアクティブな設計思想(v-model、算出プロパティ等)の相性が良い |
| 実務での実績 | Chatwoot等、同ジャンルのオープンソースプロダクトでもVue.jsの採用実績がある |

### 2.4 データベースの選定理由(MySQL)

前回(PostgreSQL)とは異なる、無料で利用可能なRDBMSとして採用。Ruby on Railsとの組み合わせ実績も豊富(mysql2 gem)。

### 2.5 インフラの選定理由(EC2 + RDS + Terraformを前回から維持)

インフラ構成はEC2(t3.micro) + RDS(db.t4g.micro)のみで構成し、前回のTerraformコードを土台にする。無料枠での運用、および既に構築済みの環境を活かす観点から、DBエンジン・アプリケーション実行環境設定のみを今回の技術スタックに合わせて調整する。

## 3. 技術選定の判断軸(参考記録)

今回の技術選定にあたり、Python + Django との比較検討も行った。要件定義(CRUD・認証・関連付け・MySQL接続)そのものに対しては、Python/Django・Ruby/Railsのどちらでも技術的に対応可能であり、決定的な優劣はない。最終的にRuby on Railsを採用した決め手は、①ジャンルでの実績、②前回(Java)との対比における設計思想の際立ち、の2点である。
