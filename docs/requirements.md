# 要件定義書：問い合わせ管理アプリ

## 1. プロジェクト概要

### 1.1 背景

本プロジェクトはスクールの課題として実施する。
前段階の「タスク管理アプリ(初級編)」で習得した技術・スキルを土台に、異なる技術スタックを用いて「認証」「テーブル間の関連付け」という、自分にとって初めて取り組む要素を加えた課題として、前回のタスク管理アプリに続いて実施する。

### 1.2 目的

問い合わせ管理Webアプリケーションを開発する。
SaaS型サブスクリプションサービスを提供する架空の企業を想定し、顧客からの問い合わせをフォームで受け付け、スタッフがステータス管理・担当者割り当て・対応履歴の記録を行える業務ツールを構築する。初級編で学習した「タスク管理アプリ」とは異なる技術スタックを使用して新しい技術を習得するとともに、フロントエンド/バックエンド/データベースの連携、認証、REST APIの構造など、Webアプリケーションが動作する仕組みそのものへの理解を深めることを目的とする。

### 1.3 利用者

| 利用者 | 認証 | 主な操作 |
|---|---|---|
| 顧客(問い合わせをする側) | 不要 | 問い合わせフォームからの送信のみ |
| スタッフ(対応する側) | 必要 | ログイン後、問い合わせの一覧確認・ステータス変更・担当者割り当て・優先度設定・コメント記録 |

前回(タスク管理アプリ)は個人利用・認証なしの構成だったが、今回は「問い合わせする側」「対応する側」という2者構造のため、担当者の関連付け・スタッフ認証を新規に導入する。

### 1.4 利用環境

| 画面 | 対応環境 |
|---|---|
| 問い合わせフォーム(顧客向け) | Web ブラウザ(PC・スマートフォン・タブレット、レスポンシブ対応) |
| スタッフ用ボード画面 | Web ブラウザ(PC を主対象。スマートフォンでは閲覧・簡易操作に対応するが、ドラッグ&ドロップ操作はPCを前提とする) |

## 2. 機能要件(概要)

問い合わせフォーム・ステータス管理(カンバンボード形式)・担当者割り当て・優先度管理・対応履歴/コメント・検索・統計ダッシュボード・メール通知(仕組みの実装のみ)の機能を提供する。

詳細は [機能要件定義書](functional-requirements.md) を参照。

---

## 3. 非機能要件

### 3.1 対応ブラウザ

| ブラウザ | バージョン |
|---------|-----------|
| Google Chrome | 最新版 |
| Microsoft Edge | 最新版 |

### 3.2 性能要件

- 画面の初期表示：3秒以内
- 問い合わせの登録・更新操作：1秒以内にレスポンスを返す
- 想定問い合わせ件数：月間300件程度(小規模SaaS企業の問い合わせ窓口を想定)

### 3.3 レスポンシブ対応

- 問い合わせフォーム：スマートフォン・タブレット・PCの全画面幅に対応する
- スタッフ用ボード画面：PCでの利用を主とするが、画面幅に応じてレイアウトを調整し、スマートフォンでも一覧閲覧・ステータス変更(プルダウン操作)ができるようにする

### 3.4 セキュリティ

- スタッフのパスワードは`has_secure_password`(bcryptによるハッシュ化)を用いて安全に保存する
- スタッフ用画面はログインセッションによるアクセス制御を行う
- SQLインジェクション・XSS等の基本的な脆弱性対策を実施する
- 問い合わせの削除機能は設けない(対応履歴・記録として保持する。実務における一般的な設計に合わせた判断)
- デモ・動作確認用のシードデータ(パスワードが公開コード上に書かれたスタッフアカウント等)は、本番環境で誤って作成されないようdevelopment環境限定にする

### 3.5 可用性

- 個人開発規模のため、稼働率保証(SLA)は定めない
- EC2は単一インスタンス構成のため、障害時の自動フェイルオーバーは行わない

### 3.6 データバックアップ

- RDSの自動バックアップ機能(AWSデフォルト設定)に従う。追加のバックアップ運用は行わない

## 4. 画面設計(概要)

問い合わせフォーム・送信完了画面・スタッフログイン画面・ボード画面・問い合わせ詳細/編集モーダルで構成する。

詳細は [画面設計書](screen-design.md) を参照。

---

## 5. データベース設計(概要)

`inquiries`(問い合わせ)・`staffs`(スタッフ)・`comments`(対応履歴/コメント)の3テーブルで構成する。前回(タスク管理)は単一テーブル構成だったが、今回はテーブル間の関連付け(外部キー)を新規に導入する。

詳細は [データベース設計書](database-design.md) を参照。

---

## 6. 技術スタック(概要)

フロントエンドに Vue.js + TypeScript、バックエンドに Ruby / Ruby on Rails、データベースに MySQL を使用する。前回(React / Java・Spring Boot / PostgreSQL)とは異なる技術スタックを採用し、応用力を養うことを目的とする。

詳細は [技術スタック](tech-stack.md) を参照。

---

## 7. インフラ構成(概要)

AWS上(EC2インスタンス1台＋RDSの最小構成、東京リージョン、Terraformで管理)にデプロイする。EC2はt3.micro、RDSはdb.t4g.micro(単一AZ、非公開)を使用する。DBエンジンはMySQL、アプリケーション実行環境はRuby on Railsとする。

詳細は [AWSインフラ構成](aws-infrastructure.md) を参照。

---

## 8. 今回のスコープに含めないもの(発展課題)

学習負荷・追加費用のリスクとのバランスを判断し、以下の項目は意図的にスコープ外とした。

| 項目 | 理由 |
|---|---|
| 本番環境での実際のメール配信(外部メールサービス連携) | 追加費用のリスクを考慮したため。メール通知の仕組み自体(ActionMailerによる生成、開発環境でのプレビュー確認)は実装し、環境ごとに配送方法を切り替え可能な設計とすることで、将来の追加を見据えている |
| リアルタイム通信(チャット等) | 今回の要件(フォーム型の非同期な問い合わせ管理)には不要なため。将来、リアルタイム性が本質的に必要なアプリ(チャットアプリ等)に取り組む際の学習項目として位置づける |
| パスワード再設定機能(自動リセット画面) | スタッフアカウントの新規登録画面を設けない方針(小規模運用)と一貫させ、パスワードを忘れた場合はRailsコンソールで管理者が再設定する運用とする |
| 顧客向け問い合わせ状況照会ページ | 実用性・独自性は高いが、認証を伴わない限定的な検索機能の設計が追加で必要なため、発展課題とする |
